# Ограничения и допущения проекта Flip Radar

## Блокирующие факторы (требуют решения пользователя)

### 1. MTProto API (внутренний маркет Telegram)
**Проблема:** Bot API не поддерживает `payments.getResaleStarGifts`. Нужна сессия обычного пользовательского аккаунта через Pyrogram/Telethon.

**Риски:**
- Telegram может банить аккаунты за автоматизацию (ToS violation)
- Требуется `API_ID` и `API_HASH` от my.telegram.org
- Сессионный файл содержит приватные ключи (высокий риск безопасности)
- Метод может измениться или быть закрыт

**Решение для MVP:**
- Создам `MockTelegramMarketAdapter` с фикстурами JSON
- Оставлю заглушку для реального MTProto-коллектора с TODO и инструкцией
- Пользователь должен сам получить API_ID/HASH и протестировать на свой риск

### 2. API маркетов MRKT, Portals, Tonnel
**Проблема:** В ТЗ указано «точных эндпоинтов нет, найти самостоятельно».

**Текущее состояние:**
- Публичные API этих маркетов не документированы
- Требуется реверс-инжиниринг мини-аппов (анализ трафика DevTools)
- Эндпоинты могут измениться без предупреждения

**Решение для MVP:**
- Создам `MockMarketAdapter` для каждого маркета с примерными данными
- Архитектура позволит заменить моки на реальные адаптеры после получения эндпоинтов
- Добавлю инструкцию по reverse-engineering в README

### 3. Цветовой анализ (монохромность)
**Проблема:** Требуется извлечение доминантных цветов из изображений подарков (анимации).

**Сложности:**
- Нужно скачивать изображения/стикеры из Telegram
- Первый кадр анимации (WebM/TGS) требует ffmpeg или библиотеки вроде opencv
- k-means кластеризация в OKLCH — вычислительно затратно

**Решение для MVP:**
- Создам предрасчитанную таблицу `attribute_colors` с моковыми `mono_score`
- Оставлю TODO-функцию для реального цветового анализа
- Логика фильтрации будет работать на моковых данных

### 4. Реальные комиссии и курсы
**Из раздела 13 ТЗ:** комиссии маркетов неизвестны, курс Stars→TON неизвестен.

**Решение:**
- Все значения в `config.yaml` (легко обновить)
- Добавлю примерные значения из ТЗ
- Пользователь должен проверить актуальные данные

## Что будет реализовано в MVP

### ✅ Полностью рабочие компоненты
1. **Архитектура:** модули `collectors/`, `engine/`, `notifier/`, `bot/`
2. **БД:** PostgreSQL с полной схемой (миграции Alembic)
3. **Mock-адаптеры:** все 4 маркета с реалистичными фикстурами
4. **Логика режима 1:** расчёт fair price, net profit, скоринг (без реального времени продажи)
5. **Логика режима 3:** `beauty_tier()` с полными тестами
6. **Логика режима 2:** фильтрация по `mono_score` из таблицы (без реального image processing)
7. **Бот (aiogram 3):** меню `/start`, `/modes`, `/deals`, настройки, форматирование алертов
8. **Тесты:** unit-тесты для всех вычислений, интеграционные тесты на моках
9. **Docker Compose:** bot, PostgreSQL, Redis, миграции

### ⚠️ Компоненты-заглушки (требуют доработки)
1. **MTProto-коллектор:** заглушка с инструкцией по настройке Pyrogram
2. **Адаптеры MRKT/Portals/Tonnel:** моки вместо реальных API
3. **Цветовой анализ:** предрасчитанная таблица вместо реального анализа
4. **История продаж:** симуляция `inferred` на моках (логика готова, данных нет)
5. **Telegram Stars оплата:** инвойсы работают, но требуют настройки провайдера

### 🔧 Что нужно от пользователя после MVP
1. Получить `API_ID`, `API_HASH` от my.telegram.org
2. Найти эндпоинты MRKT/Portals/Tonnel (инструкция прилагается)
3. Проверить актуальные комиссии и курс Stars→TON
4. Реализовать цветовой анализ (опционально, есть TODO с примером кода)
5. Настроить Telegram Stars провайдера для реальной оплаты

## Стратегия верификации

Поскольку реальные API недоступны, верификация будет проходить в два этапа:

**Этап A (сейчас):** Полная верификация на моках
- Все unit-тесты проходят
- Интеграционные тесты на `MockAdapter` проходят
- Бот запускается и отвечает на команды
- Алерты форматируются правильно (на тестовых данных)
- Docker Compose поднимается без ошибок

**Этап B (требует пользователя):** Верификация с реальными API
- Пользователь подставляет реальные адаптеры
- Запускается на 1–2 часа для сбора реальных листингов
- Проверяется корректность расчётов на реальных данных
- Проверяется отсутствие rate-limiting и FloodWait

## Критерии приёмки MVP

Буду считать работу завершённой, если:

✅ Все 8 этапов из раздела 12 ТЗ реализованы (с моками где необходимо)
✅ Все unit-тесты проходят
✅ Бот отвечает на все команды из раздела 9
✅ Алерты форматируются по шаблону из разделов 6, 7, 8
✅ Docker Compose поднимается и бот работает
✅ README содержит инструкции по замене моков на реальные API
✅ Код прошёл все проверки из Этапа 4 скилла (на доступном уровне верификации)

## Что НЕ входит в MVP

❌ Реальная интеграция с MTProto (ToS риск)
❌ Реверс-инжиниринг API маркетов (требует доступа к их мини-аппам)
❌ Реальный image processing для монохромности (вычислительно затратно)
❌ Production-ready деплой (мониторинг, алерты, масштабирование)
❌ Юридическая проверка ToS маркетов
